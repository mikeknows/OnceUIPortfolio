> This is an original, product-neutral demonstration inspired by real data-heavy application work.
> It uses synthetic data and does not reproduce an employer interface, schema, or source code.

## The problem

Administrative applications often need to expose data from many tables without rebuilding every grid
from scratch. The useful engineering question is not “how do I draw a table?” It is how to turn a
schema into predictable interface behavior while keeping validation, naming, and editing understandable.

This portfolio demo makes that mapping visible. Change the sample SQL, apply it, and the React grid
reconfigures around the detected columns.

## Interactive sandbox

The sandbox intentionally implements a small, inspectable slice of the idea:

- parses column names from a basic `CREATE TABLE` statement,
- preserves existing cell values when compatible columns remain,
- adds columns and rows through quick actions,
- maps SQL-style names into readable grid headings, and
- keeps all sample data in the browser.

## Mapping model

```typescript
type GridColumn = {
  key: string;
  label: string;
};

const toGridColumn = (sqlColumn: string): GridColumn => ({
  key: sqlColumn,
  label: sqlColumn.replaceAll("_", " "),
});
```

The live demo uses a deliberately lightweight parser, not a complete SQL grammar. A production version
would get trusted metadata from a backend endpoint, allow-list exposed tables and columns, map database
types explicitly, validate edits server-side, and apply authorization independently of the UI.

## What the demo proves

- **Schema-driven UI:** one source of column truth can configure repeated interface patterns.
- **State migration:** values survive compatible schema changes rather than resetting blindly.
- **Safe scope:** the demo is honest about what it implements and what belongs on a server.
- **Maintainability:** the transformation is small enough to inspect, test, and replace with richer metadata later.

## Where I would take it next

1. Replace the regex parser with typed metadata returned by an authenticated API.
2. Add explicit data types, formatters, validators, and accessible error states.
3. Add server-side pagination, sorting, and filtering for large datasets.
4. Test schema changes, duplicate names, invalid identifiers, and interrupted saves.

The value of this pattern is reuse without hiding complexity. A configurable grid should reduce repeated
work while still making authorization, validation, and failure behavior explicit.
