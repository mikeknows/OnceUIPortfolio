> This article is informed by general professional experience. All examples are original,
> simplified, and product-neutral; they do not reproduce any employer or production system.

SQL injection is a boundary failure: untrusted data is allowed to change the structure of a SQL
command. The primary defense is not stripping suspicious characters. It is keeping SQL structure
and user-provided values separate all the way to the database driver.

## The vulnerable pattern

```csharp
// Never concatenate untrusted values into SQL.
var sql = $"SELECT Id, Username FROM Users WHERE Username = '{username}'";
```

Quoting, escaping, and blacklists are easy to get wrong across encodings, database modes, and future
query changes. A value that is supposed to be data should always be sent as data.

## Parameterize values

### Entity Framework Core

```csharp
var user = await db.Users
    .SingleOrDefaultAsync(u => u.Username == username, cancellationToken);

// Interpolated SQL is safe here because EF converts the value into a parameter.
var activeUsers = await db.Users
    .FromSqlInterpolated($"SELECT * FROM Users WHERE Status = {status}")
    .ToListAsync(cancellationToken);
```

Use `FromSqlInterpolated` for values. Do not build a string first and pass the resulting string to a
raw SQL method; doing so loses the parameterization boundary.

### ADO.NET

```csharp
const string sql = """
    SELECT Id, Username, PasswordHash
    FROM Users
    WHERE Username = @username;
    """;

await using var command = new SqlCommand(sql, connection);
command.Parameters.Add("@username", SqlDbType.NVarChar, 80).Value = username;

await using var reader = await command.ExecuteReaderAsync(cancellationToken);
```

Specify parameter types and lengths when they are known. This documents intent and avoids driver
guesses that can cause poor query plans or unexpected conversions.

## Passwords are a separate security boundary

Parameterized SQL prevents injection; it does not make plaintext password storage acceptable. Fetch
the account by its normalized identifier, then verify the submitted password against a slow,
salted password hash using the platform's maintained password-hashing API.

```csharp
var user = await db.Users.SingleOrDefaultAsync(
    u => u.NormalizedUsername == normalizedUsername,
    cancellationToken);

if (user is null ||
    passwordHasher.VerifyHashedPassword(user, user.PasswordHash, password)
        == PasswordVerificationResult.Failed)
{
    return Unauthorized();
}
```

Authentication responses should avoid revealing whether the username or password was incorrect, and
login endpoints still need throttling, monitoring, and secure session handling.

## Values can be parameterized; identifiers cannot

Table names, column names, and sort directions are part of SQL structure. If a user can choose one,
map the choice through a small allow-list instead of inserting the raw input.

```csharp
var orderBy = requestedSort switch
{
    "name" => "DisplayName",
    "created" => "CreatedAt",
    _ => "Id"
};

var direction = descending ? "DESC" : "ASC";
var sql = $"SELECT Id, DisplayName, CreatedAt FROM Items ORDER BY {orderBy} {direction}";
```

This interpolation is acceptable only because every possible identifier is controlled by the
application. The filter values added to that query must still be parameters.

## Stored procedures are not automatically safe

A stored procedure that accepts typed parameters can provide a strong interface. A procedure that
concatenates those parameters into dynamic SQL can reintroduce the same vulnerability.

When dynamic SQL is truly necessary in SQL Server, keep identifiers allow-listed and pass values to
`sp_executesql` as parameters.

## Defense in depth

- Give the application database identity only the permissions it needs.
- Keep connection credentials in a managed secret store or protected runtime configuration.
- Encrypt database connections and verify the server certificate.
- Avoid returning database exceptions or query text to clients.
- Log request IDs and safe context, not credentials or sensitive record contents.
- Patch the database driver, ORM, framework, and database engine.
- Review raw-SQL call sites and code-generation paths as part of normal code review.

Least privilege limits blast radius, but it is not a substitute for parameterization.

## Test the boundary

Security tests should verify behavior, not merely assert that a call did not throw.

```csharp
[Theory]
[InlineData("' OR 1=1 --")]
[InlineData("'; DROP TABLE Users; --")]
public async Task FindByUsername_TreatsInputAsData(string input)
{
    var result = await repository.FindByUsername(input, CancellationToken.None);

    Assert.Null(result);
    Assert.True(await db.Users.AnyAsync());
}
```

Integration tests against the actual data-access path are especially valuable. They catch accidental
regressions when a safe ORM query is later replaced with raw SQL.

## The rule I keep coming back to

Validation protects business rules. Parameterization protects the SQL boundary. Allow-lists protect
the small pieces of SQL structure that must be configurable. Least privilege limits damage if another
control fails.

Those responsibilities are related, but they are not interchangeable—and secure systems make each
one explicit.
