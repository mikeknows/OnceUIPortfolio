Healthcare software operates where privacy, availability, and auditability are not optional. A small
workflow mistake can affect reporting, coordination, or a person's ability to receive timely service.
That changes the standard for “done.”

The HIPAA Security Rule centers on reasonable and appropriate administrative, physical, and technical
safeguards for the confidentiality, integrity, and availability of electronic protected health information.
The [HHS Security Rule summary](https://www.hhs.gov/hipaa/for-professionals/security/laws-regulations/index.html)
and [NIST SP 800-66 Rev. 2](https://csrc.nist.gov/pubs/sp/800/66/r2/final) are better sources for the
actual requirements than a portfolio article.

What I can share publicly are the engineering habits that help systems support those obligations.

## Authorization belongs at the service boundary

Hiding a button is not authorization. Every operation that reads or changes sensitive data should make
its access decision on the trusted side of the boundary, using current identity, role, scope, and the
specific operation being attempted.

```csharp
[Authorize]
[HttpGet("{recordId:guid}")]
public async Task<ActionResult<RecordSummaryDto>> GetRecord(
    Guid recordId,
    CancellationToken cancellationToken)
{
    var decision = await authorization.AuthorizeAsync(
        User,
        new RecordResource(recordId),
        RecordOperations.Read);

    if (!decision.Succeeded)
        return Forbid();

    return await records.GetSummaryAsync(recordId, cancellationToken);
}
```

The client can still tailor the interface to a user's permissions, but the API must remain correct if
someone bypasses that interface entirely.

## Audit the decision, not the sensitive payload

Useful audit events answer who acted, what operation they attempted, which logical resource was involved,
whether it succeeded, and how to correlate it with system logs. They should not duplicate the record itself.

```csharp
await audit.WriteAsync(new AuditEvent
{
    ActorId = currentUser.Id,
    Action = "record.summary.read",
    ResourceReference = auditReference,
    Outcome = "allowed",
    RequestId = HttpContext.TraceIdentifier,
    OccurredAtUtc = clock.UtcNow
});
```

Audit stores need their own access controls, retention policy, integrity protections, monitoring, and
review process. Logging everything into a general application log can create a second sensitive-data store
that nobody intended to build.

## Minimize data before protecting it

Encryption is important, but the safest field is one a component never receives. I try to ask these questions
before choosing a cipher or storage product:

1. Does this workflow need the field at all?
2. Can the API return a smaller purpose-built DTO?
3. Can the value be tokenized, truncated, or replaced with a reference?
4. How long must it exist in this subsystem?
5. Who needs to see it in logs, exports, caches, and support tools?

Data minimization reduces blast radius across application code, backups, telemetry, browser state, and
third-party services.

## Treat integrations as hostile boundaries

Even trusted partners fail in inconvenient ways. A robust integration validates both the request it sends
and the response it receives, uses explicit timeouts, retries only safe operations, and makes partial failure
visible.

```csharp
using var response = await httpClient.SendAsync(request, cancellationToken);

if (!response.IsSuccessStatusCode)
{
    await failures.RecordAsync(correlationId, response.StatusCode, cancellationToken);
    return IntegrationResult.RetryOrReview(response.StatusCode);
}

var payload = await response.Content.ReadFromJsonAsync<PartnerResponse>(cancellationToken);
return validator.IsExpected(payload)
    ? IntegrationResult.Accept(payload!)
    : IntegrationResult.ManualReview("Unexpected response shape");
```

Idempotency keys, durable state transitions, bounded retries, and reconciliation tools matter more than
an optimistic happy-path diagram.

## Protect confidentiality and integrity together

For application-level encryption, use maintained platform libraries and authenticated encryption rather
than designing a custom format. Authenticated modes such as AES-GCM protect both confidentiality and
tamper detection. The [OWASP Cryptographic Storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)
also emphasizes key management, secure randomness, and separating keys from encrypted data.

In practice, the harder questions are often operational:

- Where are keys generated and stored?
- Which identity can use them?
- How are rotation and revocation handled?
- Can backups be restored without bypassing the control?
- What happens when the key service is unavailable?
- How is access to decryption audited?

“The database is encrypted” is not an answer to all of those questions.

## Make failure safe and observable

Healthcare workflows frequently cross browsers, APIs, databases, scheduled jobs, file imports, and external
services. Failures need a clear state instead of a silent half-success.

Patterns I value include:

- explicit pending, completed, rejected, and manual-review states,
- stable correlation identifiers across service boundaries,
- idempotent processing where retries are expected,
- health checks that distinguish degraded dependencies from a healthy application process,
- alerts that explain the affected workflow rather than only reporting an exception type, and
- recovery instructions written before the incident.

Availability is not just uptime. It is the ability to detect a problem, understand its scope, and restore
the workflow without making the data less trustworthy.

## Build security into delivery

Static analysis, dependency review, protected branches, repeatable builds, staged deployments, and rollback
planning all shorten the distance between a risky change and useful feedback. None of them proves compliance
by itself. Together, they make secure behavior easier to repeat and easier to inspect.

## The practical standard

I do not describe a sample application as “HIPAA compliant.” Compliance depends on the organization,
contracts, risk analysis, policies, training, physical safeguards, operations, and the complete technical
environment—not one repository or code snippet.

The engineering goal is more concrete: make access intentional, collect less data, preserve integrity,
explain important actions, fail safely, and leave evidence that the controls are actually operating.
